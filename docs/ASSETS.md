# Launch assets

Screenshots, a walkthrough video and the README's GIF, generated by driving the
real extension in a real browser.

```bash
npm run assets
```

About 40 seconds. Output lands in `build-assets/`, which is **gitignored** —
with one exception, the README GIF, which is committed. See below.

## Why they are generated rather than committed

Two reasons, and the second is the important one.

The boring reason: they are 1.5 MB that a script rebuilds in under a minute.
Committing them makes every clone pay for them forever, and every re-capture
adds another copy to the history.

The reason that matters: a generated screenshot cannot show a state the product
does not reach. `e2e/capture.spec.ts` clicks the same buttons a user clicks,
against `dist/`, and screenshots whatever comes back. If the dashboard stops
sorting the blocked release first, the screenshot changes. A hand-composed
mockup would keep showing the old behaviour until someone noticed, which is how
store listings end up advertising features that were removed two versions ago.

The same argument applies to the states the product *cannot* reach without a
live org — see "The org shot" below.

## What you get

```
build-assets/

  raw/                         8 PNGs at 480x800, the width Chrome gives a side panel
    01-dashboard.png
    02-dashboard-blocked.png
    03-inspector-filtered.png
    04-component-detail.png
    05-approvals-queues.png
    06-approval-recorded.png

    08-org-connect-form.png
  store/                       5 PNGs at 1280x800, ready to upload
    1-dashboard.png
    2-inspector.png
    3-component-detail.png
    4-approvals.png
    5-org-connection.png
  promo/                       the two tiles the store asks for
    small-tile-440x280.png     required; a listing without one is rejected
    marquee-1400x560.png       optional, unless you want to be featured
  video/

```

`store/` is the set [`STORE-LISTING.md`](STORE-LISTING.md) §3 calls for, at the
larger of the two sizes the Chrome Web Store accepts.

## How the plates are made

The panel is 480px wide; the store wants 1280x800. Rather than stretching the
panel — which would both misrepresent it and make the text soft —
`scripts/compose-store-shots.mjs` places each screenshot at its true size on a
1280x800 plate in the icon's own background colour (`#1b2430`).

That script uses the project's own PNG codec, `scripts/lib/png.mjs`, the same
one that generates the icons. No image dependency is installed for this. The
codec reads all five PNG scanline filters and both 8-bit colour types Chromium
emits; it writes filter 0 only, because the icon check compares bytes and a
deterministic encoder is worth more there than a smaller file.

## The tiles

`scripts/build-promo-tiles.mjs` draws both promotional tiles from
`scripts/icon-design.mjs` — the same definition the icon and the SVG come from
— using the same PNG codec. So a tile cannot depict an icon the extension does
not ship, which is the failure mode of every hand-exported tile.

**Neither carries text.** The store's guidance is to keep promotional images
free of it, and there is no font renderer here; letterforms plotted by hand
would look worse than their absence. The tiles are the icon on the plate colour
with a slight vertical lift, because flat `#1b2430` at 1400x560 reads as a
rendering failure rather than a choice.

The small tile is **required**: a listing without one is rejected.
`STORE-LISTING.md` used to call it optional, which was wrong.

## The org shot

`STORE-LISTING.md` §3 row 5 asks for the connect form and treats a *connected*
org strip — instance host, last refreshed time, active Refresh button — as an
optional hand-captured replacement. **The capture run cannot reach that strip.** It
needs a live org and a completed OAuth sign-in, and Chrome's permission prompt
cannot be driven by a test in any mode.

So plate 5 is the connect form instead: the login URL, the Consumer Key field,
and the note that no client secret is accepted. That is honest and it makes the
right point — the OAuth client is one the user creates in their own org.

If you have an org, capture the connected state by hand and replace
`build-assets/store/5-org-connection.png` before uploading. Blur or use a
scratch org: no real org name, username, instance URL or deploy id may appear in
a store screenshot. See [`LIVE-ORG-RUNBOOK.md`](LIVE-ORG-RUNBOOK.md).

## The README GIF

```bash
npm run assets      # drive the extension, record the walkthrough
npm run demo-gif    # assemble docs/media/demo.gif
```

`docs/media/demo.gif` **is** committed — the one generated asset that is, because GitHub
renders it inline and a `.webm` it does not.

**No system dependency.** Frames come out of the recording using the ffmpeg that Playwright
already installs for its own video capture, so nothing needs to be on your PATH and nothing
is installed. That build is `--disable-everything`: it can decode VP8 and write PNGs, but it
has no GIF muxer and no `palettegen`, so the assembly is done by `scripts/lib/gif.mjs` — a
GIF89a encoder in the same spirit as this project's own PNG codec and ZIP writer.

Three things keep it small enough to commit:

- **Median-cut quantisation** to 255 colours. A panel screenshot has far more than that once
  text is antialiased, but they cluster tightly.
- **Frame differencing.** Index 0 is transparent and every pixel identical to the previous
  frame uses it. A mostly static panel then costs almost nothing per frame.
- **Blank-frame trimming.** The recording starts before the panel's first paint, and the
  first frame of a GIF is its poster — the still that anybody who never presses play sees.

Current output: **150 frames, 360×600, 8fps, 1.24 MB**. The budget is 5 MB, and
`build-demo-gif.mjs` exits non-zero above it. If a longer walkthrough pushes it over, lower
`FPS` or `WIDTH` in that script rather than raising the budget: a README that takes five
seconds to paint is worse than one with no GIF.

## Changing what is captured

`e2e/capture.spec.ts` is a normal Playwright test in its own project, so it can
use every assertion the e2e suite uses — and it does, because a capture run that
silently screenshots an error state is worse than one that fails.

- **Add a shot:** call `shoot('09-name')` where you want it, then add an entry to
  `PLATES` in `scripts/compose-store-shots.mjs` if it belongs in the store set.
- **Pacing:** `BEAT` is 900ms. It is what makes the video watchable rather than a
  flicker; the instinct is always to shorten it, and the instinct is wrong.
- **Text entry** goes through `typeLikeAPerson`, which types at 45ms a character.
  Filling a field instantly reads as a cut in the video.

The capture is not part of `npm run test:e2e` and CI does not run it. It
produces artefacts rather than assertions, and it takes half a minute of
deliberate waiting to do it.
