# Launch assets

Screenshots and a walkthrough video, generated by driving the real extension in
a real browser.

```bash
npm run assets
```

About 40 seconds. Output lands in `build-assets/`, which is **gitignored**.

## Why they are generated rather than committed

Two reasons, and the second is the important one.

The boring reason: they are 1.5 MB that a script rebuilds in under a minute.
Committing them makes every clone pay for them forever, and every re-capture
adds another copy to the history.

The reason that matters: a generated screenshot cannot show a state the product
does not reach. `e2e/capture.spec.ts` clicks the same buttons a user clicks,
against `dist/`, and screenshots whatever comes back. If the dashboard stops
sorting the blocked release first, the screenshot changes. A hand-composed
mockup would keep showing the old behaviour until someone noticed, which is how
store listings end up advertising features that were removed two versions ago.

The same argument applies to the states the product *cannot* reach without a
live org — see "The org shot" below.

```
  store/                       5 PNGs at 1280x800, ready to upload
    1-dashboard.png
    2-inspector.png
    3-component-detail.png
    4-approvals.png
    5-org-connection.png
  video/

```

`store/` is the set [`STORE-LISTING.md`](STORE-LISTING.md) §3 calls for, at the
larger of the two sizes the Chrome Web Store accepts.

## How the plates are made

The panel is 480px wide; the store wants 1280x800. Rather than stretching the
panel — which would both misrepresent it and make the text soft —
`scripts/compose-store-shots.mjs` places each screenshot at its true size on a
1280x800 plate in the icon's own background colour (`#1b2430`).

That script uses the project's own PNG codec, `scripts/lib/png.mjs`, the same
one that generates the icons. No image dependency is installed for this. The
codec reads all five PNG scanline filters and both 8-bit colour types Chromium
emits; it writes filter 0 only, because the icon check compares bytes and a
deterministic encoder is worth more there than a smaller file.

## The org shot

`STORE-LISTING.md` §3 asks for a *connected* org strip — instance host, last
refreshed time, active Refresh button. **That state is not reachable here.** It
needs a live Salesforce org, and nobody has connected one.

So plate 5 is the connect form instead: the login URL, the Consumer Key field,
and the note that no client secret is accepted. That is honest and it makes the
right point — the OAuth client is one the user creates in their own org.

If you have an org, capture the connected state by hand and replace
`build-assets/store/5-org-connection.png` before uploading. Blur or use a
scratch org: no real org name, username, instance URL or deploy id may appear in
a store screenshot. See [`LIVE-ORG-RUNBOOK.md`](LIVE-ORG-RUNBOOK.md).

## Turning the video into a README GIF

The README has a placeholder pointing at `docs/media/demo.gif`. That file is
**not** generated, because a GIF is one of the few things worth committing: it
renders inline on GitHub, where a `.webm` does not.

With ffmpeg installed:

```bash
# A palette first, then the GIF. One pass gives you 256 dithered colours chosen
# from the first frame, which turns the panel's greys into mud.
ffmpeg -i build-assets/video/walkthrough.webm \
  -vf "fps=12,scale=480:-1:flags=lanczos,palettegen=stats_mode=diff" \
  -y build-assets/palette.png

ffmpeg -i build-assets/video/walkthrough.webm -i build-assets/palette.png \
  -lavfi "fps=12,scale=480:-1:flags=lanczos[v];[v][1:v]paletteuse=dither=bayer:bayer_scale=3" \
  -y docs/media/demo.gif
```

Then check the size. GitHub renders an inline image up to about 10 MB, but a
README that takes five seconds to paint is worse than one with no GIF, so keep
it **under 5 MB**. If it is over:

- drop to `fps=10` — the walkthrough has deliberate pauses and loses nothing;
- trim to the first 20 seconds with `-t 20`, which covers dashboard through
  approval;
- `scale=400:-1`, which is still legible for a panel this dense.

Finally, replace the placeholder block in `README.md` with:

```markdown
![sf-releaselens walkthrough](docs/media/demo.gif)
```

## Changing what is captured

`e2e/capture.spec.ts` is a normal Playwright test in its own project, so it can
use every assertion the e2e suite uses — and it does, because a capture run that
silently screenshots an error state is worse than one that fails.

- **Add a shot:** call `shoot('09-name')` where you want it, then add an entry to
  `PLATES` in `scripts/compose-store-shots.mjs` if it belongs in the store set.
- **Pacing:** `BEAT` is 900ms. It is what makes the video watchable rather than a
  flicker; the instinct is always to shorten it, and the instinct is wrong.
- **Text entry** goes through `typeLikeAPerson`, which types at 45ms a character.
  Filling a field instantly reads as a cut in the video.

The capture is not part of `npm run test:e2e` and CI does not run it. It
produces artefacts rather than assertions, and it takes half a minute of
deliberate waiting to do it.
